# HEAV3NS-CODE native client

This surface follows the user's **Primary product design and implementation specification v0.1, September 29, 2026**. The CLI's root PRODUCT.md continues to describe the terminal product.

The operating mode is **Operate**: communicate intent, observe LUMI, inspect evidence, approve or stop work. The user need not edit code. This is an AppKit macOS application, with a proposed macOS 14+ arm64 baseline. Four independent workspace windows belong to one GUI process.

The user approved [journey-v3](../ui-prototypes/journey-v3/) for native implementation on September 30, 2026. Human–agent conversation owns the workspace: projects and conversations on the left, a dominant central conversation and persistent composer, and supporting Walkthrough / Changes / Code context on the right. Welcome and a searchable recent/pinned project library precede workspace entry without requiring authentication. Browser-based ChatGPT sign-in is optional; users choose their existing provider and model from the workspace. Retain semantic system colors, system typography, familiar macOS window/focus/selection/keyboard behavior, and read-only code inspection. IDE conventions supply file paths, declaration navigation, and change status; code is secondary to conversation. The generated SwiftUI-looking snippets are illustrative; the implementation remains Swift/AppKit.

LUMI owns execution, credentials, prompts, context, permissions, tools, cancellation, and persistence. BroccoliDB remains the runtime substrate. Swift owns presentation and native lifecycle. New desktop capabilities must be negotiated; unsupported operations must not appear to work.

The shared Code surface is now named Inspect to include file contents, recorded run evidence and Conversation Context (⌘9). Context inspection reports retained history, summaries and memory from the selected conversation, with explicit freshness and links to existing controls. It does not execute work or estimate context quality. Memory and context inspection failures leave execution controls available. Retained History opens actual active messages and rolling summaries through Context’s Open… menu, with stable read-only paging, native Find and Reload. It remains separate from saved memory and the complete assembled provider request.

Check Code extends that secondary inspector for saved JavaScript/TypeScript files when the runtime advertises `spider-check-v1`. Native inspection and the agent's `spider_check` share bounded syntax, static local-import and advisory cycle evidence, with located findings, coverage limits and a dated observation. Reload checks current saved files. Prepare Review appends to the existing draft without truncation; Send remains required before agent work. This does not replace project type checks or tests, prove complete coverage, or apply automatic repairs. See [Spider code checks](../docs/desktop/SPIDER-CODE-CHECKS.md) for the shared runtime boundary and verification.

Saved State extends Inspect when `runtime-state-v1` is available, through the Workspace menu and Workspace Actions. It reports the selected conversation's 20 most recently updated saved instructions, checksum and legacy coverage, interrupted work, a next action and a dated observation. Open Instruction… connects to Run Details and its related evidence; Find, Back/Forward and Reload retain existing navigation. Inspection neither replays work nor restores project files; reviewed Checkpoints retains project-file restore. A matching checksum establishes saved-content consistency, not instruction correctness or passing project checks. See [runtime saved state](../docs/desktop/RUNTIME-STATE-STORE.md) for persistence and recovery limits.

The project library also supports explicit user-directed creation of an empty project folder: a name/location sheet creates a new directory exclusively, then opens the normal workspace. This native bootstrap does not generate files, initialize Git, or run an agent instruction. Existing folders are opened through the separate Open action. The library sorts projects by opened time, filesystem modification time, folder creation date, or name, showing path and date/time context for duplicate names.

User messages must be visually distinct from agent replies. Automatic before/after Git checkpoints connect project versions to instructions, with flags, reviewed restore, a safety copy and a new conversation that preserves the original. A supporting Run panel offers detected/custom commands, local process control, console output and an explicit browser preview. Browser-ready HTML apps offer Preview App: the runtime starts a local preview and opens it in the default browser without requiring the user to find index.html, install a server, or configure a command. These are workspace tools around the conversation; they do not make code the primary surface. See [checkpoint and Run behavior](../docs/desktop/CHECKPOINTS-AND-RUN.md) for the exact recovery and execution scope.

The current deliverable brings the approved journey into the existing native application and durable runtime. Native production code and a local signed development build do not establish public distribution readiness. See [journey implementation](../docs/desktop/JOURNEY-V3.md), [integration boundary and build procedure](../docs/desktop/INTEGRATION.md), and the [earlier evidence report](../docs/desktop/RELEASE-EVIDENCE.md) for implemented and unverified boundaries.
